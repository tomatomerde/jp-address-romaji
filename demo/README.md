# デモページ

ブラウザだけで動くデモの元ファイル。`.github/workflows/pages.yml` が
build → ブラウザ検証 → GitHub Pages へのデプロイまでを行う。
公開先は `https://tomatomerde.github.io/jp-address-romaji/`。

## 手元で動かす

```sh
./demo/build.sh          # demo/_site を組み立てる（レジストリから公開版を取得する）
pnpm test:demo           # 組み立てた _site を実際の Chromium で検証する
npx serve demo/_site     # 目で見たいとき（http で配る必要がある。ESM は file: で動かない）
```

`demo/_site` と `demo/_work` は生成物なので commit しない（`.gitignore` 済み）。

## この案件だけの難所はデータ配信

姉妹デモ（itaiji-normalize・japan-calendar）はデータをライブラリに焼き込んでいるので、
ページは読み込み後1件もリクエストを出さない。このライブラリはそうならない——ブラウザには
ファイルシステムが無く、住所データは `configureDataSource({ endpoint })` で
**自分が配信するもの**を指す構成だから、変換のたびに市区町村ファイルを取りに行く。

したがってこのページは「0件です」と言えない。代わりに
**出したリクエストを全部並べて、そこに番地から先が無いことを見せる**ほうを主張にしている。
`scripts/verify-demo.mjs` は、建物名と宛名を付けた住所を実際に打ち込んでから、
ブラウザが出した全 URL を走査して、その断片が1つも含まれていないことを検査する。

## 決めたことと、覆すときにどこを触るか

| 決定 | 理由 | 覆すとき |
| --- | --- | --- |
| **npm 公開版を固定して読み込む**（このリポジトリのソースをビルドしない） | 訪問者が `npm install` して得るものと、ページで見えるものを一致させるため。作業中のツリーを載せると、まだ誰も入手できない挙動を宣伝することになる | `demo/pinned-version.txt` |
| **データも npm 公開版から取る**（`jp-address-romaji-data` の tarball を展開してコピー） | 同じ理由。生成し直すと Geolonia への通信が要るうえ、訪問者が入手するバイト列と一致する保証が無くなる | `demo/pinned-data-version.txt` |
| **町データは必要な市区町村だけ配る** | 全国は約1,900ファイル・展開後 100MB 超。1回の変換が読むのは索引1つと市区町村1つだけなので、全部置く理由が無い | `demo/municipalities.txt`（1行 `<都道府県>/<市区町村>`。build.sh がここからコピーとマニフェスト生成の両方を行う） |
| **索引 `ja.json` は削らずに丸ごと配る** | 索引を削ると、実在する市区町村をライブラリが「存在しない」と答える。それは欠落ではなく**誤答**で、このライブラリがいちばん避けたい失敗の形をデモがやることになる | `build.sh` の `cp "$dataset/data/ja.json"` |
| **`exports` 経由でバンドルする**（tarball の `dist/index.js` を直接指さない） | パス指定だと **Node 用のビルド**が黙って入り、`browser` 条件が配線されているかを何も検査しないバンドルができる。使い捨てプロジェクトに install してベア指定子で入口を書くのはそのため | `build.sh` の consumer セットアップ |
| **ページが述べる数値を、ライブラリと生成物から読む** | 都道府県数はライブラリの `PREFECTURES`、配信中の市区町村と各ファイルのサイズは build が生成した `served-data.js`、全国の市区町村数と索引の gzip サイズは build が焼き込む。焼き込んだ2つは `verify-demo.mjs` が `_site` から再計算して突き合わせる | `app.js` の `renderFacts` と `index.html` の `data-fact` |
| **外部リクエストをゼロにする**（Web フォント・CDN・解析タグを一切使わない） | このページの主張は「出したリクエストの一覧」そのものなので、住所と無関係な行が混じると、一覧を読む意味が薄れる | `demo/style.css`（フォント指定）と `demo/index.html` |
| **ページの言語は日本語** | 日本の住所を扱うのは日本語で業務を書いている人で、流入も日本語の記事から来る。README を英語基準にしている方針とは読み手が違うので衝突しない | `demo/index.html`（英語版を足すなら別ファイルにして相互リンク） |
| **京都市中京区（665KB）を配る** | データセット最大の市区町村ファイル。通り名住所というこのライブラリ固有の機能を見せる枠であると同時に、「市区町村ごとに1ファイル」が**小さいファイル**を意味しないことを、サイズ一覧で正直に見せる枠でもある | `demo/municipalities.txt` |

## 「受け付ける形／受け付けない形」パネルが本体の検査になっている

パネル4は、代表的な入力を**その場で実行して**結果を並べる。各ケースには
`expect: 'accept' | 'refuse' | 'throw'` を持たせてあり、**実際の挙動がそれと食い違うと
ページに警告が出て、`scripts/verify-demo.mjs` が落ちる**。

デモは npm 公開版を読み込んでいるので、**公開済みの版が受け付ける入力の範囲が変わったとき、
このリポジトリでそれに気づく仕掛けは他に無い**（本体のテストは本体のソースに対して走る）。

`expect` が3値なのは、公開版が実際に例外を投げる経路が1つあるため（下記）。
`throw` を `refuse` に丸めると、**型付きの失敗と未捕捉の例外の違い**が消える。
このライブラリのエラー設計はまさにその区別の上に立っているので、そこは丸めない。

## デモを作る過程で出た本体側の不具合（イシュー #58）

**エンドポイントが持っていない市区町村ファイル（HTTP 404）を、順方向の `toRomaji` が
値ではなく例外にする。** 逆方向の `fromRomaji` は同じ状況を
`DATA_NOT_CONFIGURED`（「東京都渋谷区の町データが無い」）として正しく返す。

- 原因は経路の違い。逆方向はこのパッケージ自身の `dataAccess.ts` が読んでいて
  `response.ok` を見るが、順方向は正規化を `@geolonia/normalize-japanese-addresses` に
  委譲していて、そちらが 404 の本文を `response.json()` に渡して `SyntaxError` になる。
  `toRomaji` はそれを捕まえていない
- **README が勧めている構成で起きる。** 「必要な市区町村だけを配信することもできます」と
  書いてある以上、404 は異常系ではなく通常の運用
- ページ側では例外を捕まえて「このデモが配っていない市区町村です」と表示している。
  直った版を pin したらパネル4の `expect` を `throw` → `refuse` に変えること
  （忘れてもページが警告を出し、`pnpm test:demo` が落ちる）

## デモ側で見つけて直した欠陥

いずれも実際に動かして測って出たもので、コードを読んでいるだけでは見えなかった。
姉妹案件で出た4件と同じ種類なので、次にデモを作るときの目の付けどころとして残す。

- **要約したルールが実測と食い違っていた。** ヘッダのメーターに「同じ市区町村を続けて
  変換しても増えません」と書いていたが、順方向と逆方向は**別々のキャッシュ**を持つので、
  逆方向のプリセットを押したあと同じ市区町村を順方向で変換すると1件増える。
  訪問者が2クリック目で自分のブラウザで反証できる文章だった。方向ごとに1回ずつ出ることを
  明記し、`verify-demo.mjs` が「同方向の2回目は0件・逆方向の初回は1件・その2回目は0件」を
  実測して固定するようにした
- **配っていない市区町村で、キーストロークごとにリクエストが出ていた。** 404 はどこにも
  キャッシュされないので、`東京都渋谷区神南一丁目1-1` を1文字ずつ打つと**9件**出た。
  読ませたい一覧が同じ 404 で埋まるうえ、実際の住所フォームなら普通やらない挙動。
  入力を 0.25 秒デバウンスし、そう書いた。`verify-demo.mjs` が実際に1文字ずつ打って
  2件以下であることを検査する（デバウンスを外すと9件で落ちる）
- **リクエスト一覧に上限が無かった。** 上の件を直しても、根気よく打てば伸び続ける。
  直近40件で打ち切り、**打ち切ったことと省略件数を明記**するようにした（合計件数は
  そのまま数え続ける）。黙って切ると、「このページが送った全部」として出しているものが
  「一部」に変わる
- **`?v=…` の説明を全行に繰り返していた。** 上流の正規化器が付けるキャッシュ回避の
  クエリ（索引 `ja.json` の `meta.updated`）で、行ごとに同じ注記が出ていた。
  パネルの説明文に1回だけ書く形にした
- **日本語の段落を折り返していたせいで、文中に空白が入っていた。** HTML では日本語文字の
  間の改行が空白としてレンダリングされる。`index.html` の日本語段落は1段落1行で書く
  （ファイル冒頭にコメントで残してある）

## リリースのたびに要る作業

新しいバージョンを publish したら **`demo/pinned-version.txt`（ライブラリ）と
`demo/pinned-data-version.txt`（データセット）のうち、上げたほうを上げる**。
上げないとページは古い版の挙動を見せ続ける。忘れても静かに壊れるだけなので、
`build.sh` はレジストリの `latest` と食い違うときに warning を出し、
`pages.yml` の週次 `pin-freshness` ジョブが**2つとも**照合して赤くする
（`docs/releasing.md` にも手順として書いてある）。

## なぜ検証をワークフローに入れてあるか

ページは訪問者に約束している——**何も打たなくても結果が見える**こと、
**確認できないものは断る**こと、そして
**番地・建物名・宛名はサーバーに届かない**こと。最後のものは本物のエンジンでしか
確かめられないので、`scripts/verify-demo.mjs` が Chromium で実際に操作して、
ブラウザが出した URL を全部走査して検証する。デプロイはその後にしか進まない。
約束を書いたページを、約束を確かめずに配らないため。
